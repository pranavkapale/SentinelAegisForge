# Architecture overview

## Current architecture

Phase 29 verifies recovery and bounded local workload behavior of the real Scala-to-research shadow path across two independently buildable modules in one repository:

- `streaming-engine` is a Scala 2.13/JDK 21 build with a version 1 transaction domain contract, pure candidate validation, a deterministic seeded simulator, explicit Apache Avro mapping, a bounded registry-backed Kafka producer, Spark 4.2.0 Structured Streaming ingestion, a local Delta 4.4.0 validated-record audit table, a separate watermark-bounded event-ID deduplication table, a customer-keyed activity lifecycle, two prior-only rolling customer features, prior-observed statistical amount features, and stateless deterministic advisory risk decisions. It contains no ML or enforcement capability.
- `model-control-plane` is a Python 3.13 package with pytest, Ruff, and mypy. It reads fixed corrected Delta feature versions through delta-rs/Arrow, joins independent delayed labels, builds immutable offline snapshots, trains one local temporal logistic baseline, indexes verified immutable runs in local SQLite-backed MLflow, reconstructs a locally executable offline candidate after archived-prediction equivalence checks, catalogs it as a research-only Registry version, assesses validation evidence, freezes offline predictions for point-in-time outcome monitoring, compares label-free feature/score distributions, assembles evidence-linked manual investigation packets, verifies source-neutral local feedback histories, executes a bounded local research replay, and separately reconstructs committed feature-row availability into immutable segments/outbox and durable no-side-effect receipts. It has no approved model or serving lifecycle.
- The repository root provides pinned, single-node Apache Kafka 4.3.1 and Confluent Schema Registry 8.3.2 runtimes for local development. Infrastructure provisions `transactions.raw` and its `transactions.raw-value` schema subject; the separate Phase 25 command explicitly provisions `features.ready` for research notifications.
- `contracts/events/transaction-event-v1.avsc` is the canonical Avro value schema. Published records use UTF-8 `customer_id` keys and registry-managed Avro values.
- Root verification, repository hygiene, baseline CI, this architecture overview, and architecture decision records provide shared engineering conventions.

The Scala module can publish bounded deterministic samples to local Kafka, consume them with registry-aware validation, durably append every validated record plus Kafka coordinates, and derive a separate event-ID-deduplicated Delta table. Phase 8 independently appends customer activity lifecycle snapshots; Phase 9 appends per-transaction prior-only event-time rolling features; Phase 10 consumes those feature rows to append prior-observed Welford amount statistics. Retried micro-batches use table-specific stable Delta transaction identifiers. Spark 4.2 requires RocksDB for these `transformWithState` queries. Monetary feature semantic v2 uses customer+currency membership: rolling velocity stays customer-wide, rolling monetary sums use the current currency, and Welford state is independently keyed and expired per customer-currency pair. Raw amounts in different currencies are never combined in these feature baselines; no FX conversion exists. Fresh v2 output/checkpoint/transaction-ID lineages supersede the old Phase 9/10 monetary semantics without rewriting historical rows (see [ADR-020](../adr/ADR-020-currency-safe-monetary-feature-semantics.md)). These boundaries do not provide lifetime uniqueness, retrospective feature correction, or a general end-to-end exactly-once guarantee. Module B now consumes already materialized local corrected feature artifacts; no online model/control-plane integration exists.

Phase 11 consumes only `transaction_statistical_features_v2` with pure ordered R001 velocity, R002 positive READY z-score and R003 combined rules. It preserves every source feature/lineage column and appends CLEAR/REVIEW, ordered rule/reason arrays and version/fingerprint to `transaction_risk_decisions`. There is no stateful operator or RocksDB setting in this query. Explicit thresholds are engineering policy, not production calibration. Decisions are advisory data, not payment actions or numeric scores. A dedicated checkpoint and Delta transaction identity protect source resume and batch retries, not lifetime event+policy uniqueness. See [deterministic risk engine](deterministic-risk-engine.md), [ADR-021](../adr/ADR-021-deterministic-risk-policy.md) and [ADR-022](../adr/ADR-022-risk-policy-versioning.md).

Phase 12 independently joins feature event IDs to FRAUD/LEGIT outcome revisions, never rule dispositions. It rejects duplicate source IDs, corrupt features and invalid/uncausal label histories, filters ingestion/label availability at AS_OF_TIME and excludes unlabeled events. Snapshots preserve monetary decimals and lineage but declare a separate candidate model-feature allowlist. Dataset identity, source schema and logical-data fingerprints make local builds inspectable and reproducible; they are not model-quality claims. See [offline ML dataset](offline-ml-dataset.md), [ADR-023](../adr/ADR-023-delayed-fraud-label-contract.md) and [ADR-024](../adr/ADR-024-offline-ml-dataset-snapshots.md).

Phase 13 verifies a Phase 12 snapshot before fitting. It splits by explicit ingestion-time boundaries, gates training labels by `train_end`, fits one training-only sklearn preprocessing/logistic pipeline, then writes separate validation/test predictions and metrics with dataset provenance. The preserved four-row labeled snapshot fails eligibility as intended. See [offline ML baseline](offline-ml-baseline.md), [ADR-025](../adr/ADR-025-temporal-ml-evaluation.md) and [ADR-026](../adr/ADR-026-logistic-regression-baseline.md).

Phase 14 adds a versioned, bounded deterministic Scala scenario generator with separate publishable transaction plan and private synthetic outcome truth. Three chronological waves use the existing registry-backed producer and the full validated → deduplicated → rolling v2 → statistical v2 Delta lineage; their IDs and Kafka acknowledgement coordinates are reconciled before the existing Phase 12 snapshot builder and unchanged Phase 13 trainer run. Independent delayed labels include revisions and deliberately unlabeled rows. The resulting evaluation is synthetic-only integration evidence, not a production fraud-quality claim. See [synthetic fraud corpus](synthetic-fraud-corpus.md), [ADR-027](../adr/ADR-027-deterministic-synthetic-fraud-corpus.md) and [ADR-028](../adr/ADR-028-synthetic-corpus-integration-and-evaluation.md).

Phase 15 verifies the immutable Phase 13 run and Phase 12 snapshot, then logs their existing configuration, metrics and small provenance artifacts to an explicit local SQLite-backed MLflow experiment. The deterministic training-run ID remains canonical; MLflow's run ID is a separate tracking address. An optional corpus identity requires explicit Phase 14 reconciliation rather than directory-name inference. Sequential retries read back exact values and hashes; partial/conflicting records fail closed. No training, model artifact or promotion is added. See [MLflow experiment tracking](mlflow-experiment-tracking.md) and [ADR-029](../adr/ADR-029-local-mlflow-experiment-tracking.md).

Phase 16 verifies those source artifacts, reconstructs Phase 13's original training-only Pipeline, compares all validation/test probabilities against the archived predictions, and saves a local MLflow/skops model candidate. Candidate identity is semantic; separate file hashes protect bytes. Inspection rechecks source, artifact and inference contracts before offline scoring. This is technical artifact verification on synthetic evidence, not registration, approval, serving or production fraud quality. See [model candidate artifact](model-candidate-artifact.md) and [ADR-030](../adr/ADR-030-reproducible-model-artifacts.md).

Phase 17 verifies the candidate and source lineage before adding an MLflow Registry version in the same local SQLite backend. The version points to the retained local Phase 16 model directory; read-back checks its metadata and hashes. Governance is `REGISTERED_RESEARCH_ONLY` with production eligibility false. The candidate ID, Phase 15 tracking run ID, and Registry model/version are distinct. No alias, promotion or serving exists. See [Registry governance](model-registry-governance.md) and [ADR-031](../adr/ADR-031-model-registry-candidate-governance.md).

Phase 18 assesses the exact Registry version against explicit evidence requirements without changing it. Technical and provenance evidence is verified, but representative quality, calibration, operational evidence and approval are not established; the outcome is production-ineligible. See [model validation governance](model-validation-governance.md) and [ADR-032](../adr/ADR-032-model-validation-evidence-policy.md).

Phase 19 freezes label-free offline probabilities from an exact Registry version and corrected Delta version in a post-training ingestion-time window, then separately resolves independent synthetic outcomes at explicit cutoffs. Immutable snapshots report scored-population coverage, revision changes, matured-subset quality and supported descriptive segments. This is historical offline replay, not proof of model availability at original ingestion or production monitoring; it cannot alter Phase 18 eligibility. See [offline delayed-outcome monitoring](offline-delayed-outcome-monitoring.md) and [ADR-033](../adr/ADR-033-offline-prediction-ledger-and-delayed-outcome-monitoring.md).

Phase 20 partitions one verified Phase 19 ledger into two explicit non-overlapping UTC ingestion-time windows, reconciles their rows to the pinned corrected statistical Delta source, and records all 11 candidate feature distributions plus the frozen prediction distribution. Numeric KS/PSI and categorical TVD/JS values are descriptive; exact decimal source values are unchanged and monetary magnitudes have currency-specific diagnostics. The local synthetic reference is not a production baseline. No labels, model inference, drift alerts, Registry mutation or production-quality conclusion enter this path. See [offline distribution monitoring](offline-distribution-monitoring.md) and [ADR-034](../adr/ADR-034-offline-feature-and-prediction-distribution-monitoring.md).

Phase 21 re-inspects a selected Phase 20 snapshot and ledger, optionally adds compatible Phase 19 T1/T2 label-maturity and Phase 18 governance context, and publishes an immutable diagnostic packet with field-level evidence references and a manual runbook. It separates ingestion-cohort distribution changes from label-observation cutoff changes, preserves unavailable metrics as limitations, and never assigns a severity or automatic action. See [offline monitoring investigation](offline-monitoring-investigation.md) and [ADR-035](../adr/ADR-035-offline-monitoring-investigation-and-runbooks.md).

Phase 22 verifies strict provider-style notifications against one fixed corrected Delta event universe, preserves complete case revisions in immutable feedback ledgers, and resolves confirmed/pending/retracted states at explicit receipt-time cutoffs. A separate versioned monitoring snapshot joins eligible confirmed outcomes to unchanged Phase 19 predictions; the old Phase 12 label and Phase 19 snapshot contracts remain intact. Current fixtures are hand-assigned synthetic statuses, not authenticated external fraud outcomes. See [durable outcome feedback](durable-outcome-feedback.md) and [ADR-036](../adr/ADR-036-durable-outcome-feedback-ingestion.md).

Phase 23 plans deterministic request identities from the verified fixed corrected statistical Delta source, executes the exact research-only Registry version locally with one trusted model load, records terminal success/failure for each request, and compares successful probabilities to the unchanged Phase 19 prediction ledger. Repeated local deliveries are logically idempotent within the bounded execution; conflicting identity reuse fails. The historical transaction ingestion timestamp does not establish feature-readiness time, and this runner has no live Kafka/HTTP transport or enforcement path. See [controlled shadow inference](controlled-shadow-inference.md) and [ADR-037](../adr/ADR-037-controlled-non-enforcing-shadow-inference.md).

Phase 24 reads the retained statistical Delta versions one by one, validates the full 25-column source, and assigns each event to its first committed version. It rejects changed/deleted rows and publishes immutable per-version segments plus a contiguous outbox. A separate bounded receiver records one durable logical receipt per ready-event ID, recognizes identical replay and derives progress from receipts. The preserved Phase 14 run is **historical commit reconstruction**: it proves logical Delta visibility under retained history, not original online feature-ready time, latency or atomic Delta-plus-outbox delivery. No scoring, Registry mutation or enforcement occurs. See [feature availability handoff](feature-availability-handoff.md) and [ADR-038](../adr/ADR-038-commit-aware-feature-availability-outbox.md).

Phase 25 verifies that outbox before preparing an immutable, bounded Kafka batch. Scala publishes exact versioned notification bytes to the explicitly provisioned `features.ready` topic, journals individual broker acknowledgements, and independently consumes them with durable per-ready-ID receipts before partition-scoped offset commits. Initial delivery, explicit replay, crash-window recovery and broker record/receipt reconciliation are separate observable boundaries. Notification values carry source Delta identity and row fingerprints, not feature values or labels. This local plaintext, single-broker path does not atomically couple Delta commits to Kafka, establish original wall-clock feature availability, execute a model, or provide production HA/security. See [Kafka feature-ready transport](feature-ready-kafka-transport.md) and [ADR-039](../adr/ADR-039-feature-ready-kafka-transport.md).

Phase 26 uses a separate stable Kafka consumer group and receipt root to seal a fully reconciled notification inbox. An independent bounded Python worker resolves exact first-visible Delta versions, checks the registered research candidate, persists one local logical result per inference request and compares scored post-training events to the immutable Phase 19 ledger. The preserved source was reconstructed from historical commits; this is not a contemporaneous commit-to-inference latency demonstration, a production model service or a payment action. See [Kafka shadow inference](kafka-research-shadow-inference.md) and [ADR-040](../adr/ADR-040-kafka-triggered-research-shadow-inference.md).

Phase 27 adds a separate bounded research stream over successive committed Delta versions, with an isolated operational Kafka group, durable accepted receipts, independently resumable inference and downstream-only publication backpressure. Its original verification source was a controlled feature fixture. See [incremental shadow operations](incremental-shadow-operations.md) and [ADR-041](../adr/ADR-041-incremental-shadow-operations-and-backpressure.md).

Phase 28 uses a new deterministic transaction corpus and a recorded `transactions.raw` offset fence, then runs all four existing Scala/Spark-to-Delta stages in three bounded waves with the same checkpoints and transaction application IDs. Commit-aware discovery hands actual statistical features to a separately fenced `features.ready` research group. Exact event-ID reconciliation, research-only results, a controlled Kafka outage, worker pause/backpressure, validated-ingestion retry and independent scoring parity are local integration evidence. These `AvailableNow` invocations do not constitute a continuously running deployment or a production latency claim. See [stateful streaming to shadow integration](stateful-streaming-shadow-integration.md) and [ADR-042](../adr/ADR-042-stateful-streaming-to-shadow-integration.md).

Phase 29 reuses that path in four independent bounded lineages: clean baseline, changed customer/currency population, actual statistical-sink post-commit failure, and downstream broker/worker interruption. An opt-in hook fails only after a durable statistical Delta append. The same RocksDB checkpoint and Delta transaction identity recover without changing committed feature values; independently checked later history distinguishes retained state from watermark-driven expiry/reactivation. Structured Spark progress, source retention, partition composition, invocation timings, local file sizes and exact source-to-result reconciliation feed an immutable reliability dossier. The harness honors configured inference tick limits. The local Python feature reader uses Arrow's native filesystem to avoid an observed interpreter-shutdown deadlock, without changing source versions or values. These experiments add no tuning, model approval, deployment or production-capacity guarantee. See [stateful streaming reliability](stateful-streaming-reliability.md) and [ADR-043](../adr/ADR-043-stateful-streaming-reliability-and-capacity.md).

## Target architecture

The following is a future direction, not a description of implemented behavior:

```text
transactions
    ↓
Kafka
    ↓
Scala/Spark streaming engine
    ↓
features + decisions
    ↓
durable/streaming outputs
    ↓
Python model control plane
    ↓
drift / delayed labels / retraining
    ↓
approved model
    ↓
streaming engine
```

Runtime and data technologies will be introduced only when their requirements and operational semantics can be evaluated.

## Engineering principles

1. Correctness before scale.
2. Recovery before optimization.
3. Distributed-system semantics must be explicit.
4. State must be bounded.
5. Event-time behavior must be tested.
6. Idempotency must have defined boundaries.
7. Do not make unconditional "exactly once" claims.
8. Do not make performance claims without reproducible evidence.
9. Production behavior matters more than framework count.
10. Prefer local-first development.
11. Important decisions require architecture decision records (ADRs).
